# FlowDesk technical architecture — approved baseline (Phase 0)

## Product shape
FlowDesk is a multi-tenant business-workspace SaaS. The first implementation uses a modular monolith: one NestJS API deployable, with bounded modules, one PostgreSQL database, and a React SPA. This keeps operational complexity low while preserving clear module boundaries. Microservices are intentionally deferred until scale and ownership boundaries justify them.

## Repository layout

```text
flowdesk/
  src/
    app/                 # app shell, providers and global composition
    components/          # reusable cross-feature UI and error handling
    features/
      auth/              # signup, login, verification and recovery UI
      workspace/         # workspace pages and domain view components
    layouts/             # shared application layouts (next extraction target)
    services/            # typed HTTP clients and API adapters
    styles/              # global design system
  backend/
    src/
      auth/              # identity, session, verification, recovery, TOTP
      common/             # shared guards/interceptors/filters (expansion point)
      health/             # readiness endpoint
      mail/               # transactional email transport
      prisma/             # Prisma service
    prisma/               # schema and versioned SQL migrations
  docs/
```

## Backend modules and boundaries
- **Auth/Identity:** registration, credential verification, email verification, password reset, TOTP, recovery codes and server sessions.
- **Workspace:** workspace and membership schema is laid down; workspace APIs and tenant-scoped business records are Phase 4+.
- **Authorization:** platform roles and workspace roles are modelled; enforcement and policy decorators are Phase 5.
- **Business domains:** projects, tasks, CRM, invoices, calendar and analytics are separate future Nest modules. They must never share arbitrary cross-tenant queries.
- **Admin:** separate protected administration module and audited operations are future admin phases.

## Database baseline
PostgreSQL is the source of truth. Prisma schema/migrations are versioned. IDs are opaque CUIDs generated by Prisma Client. Email is normalized to lowercase before lookup. Session, verification, reset and recovery tokens are stored as SHA-256 hashes, never as raw bearer secrets. TOTP shared secrets are encrypted at rest with AES-256-GCM using `TOTP_ENCRYPTION_KEY`.

## API conventions
- Prefix: `/api/v1`.
- JSON request/response bodies, except `204 No Content` operations.
- Resource nouns, lower-kebab-case paths, HTTP verbs express operations.
- DTO validation at the API boundary; whitelist and reject unknown properties.
- Cookie-based session auth; browser requests use `credentials: include`.
- Errors use Nest standard status codes and JSON `{ statusCode, message, error }` payloads.
- Health: `GET /api/v1/health`.
- Authentication endpoints are documented in `API.md`.

## Authentication and session design
- Passwords hashed with bcryptjs (cost 12); server never returns password hashes.
- Registration creates a pending user and a 24-hour email verification token.
- Email verification activates the account.
- Login creates a cryptographically random opaque session token; only its SHA-256 hash is stored.
- Session cookie is HttpOnly, SameSite=Lax, path `/`, and Secure in production; expiration is configurable.
- Session guard checks the database, expiry and account status on protected API calls.
- Password reset tokens expire after one hour and reset revokes all existing sessions.
- TOTP is optional; recovery codes are one-use and stored hashed.
- Session listing and per-session revocation are supported.

## Authorization model
Platform role: `USER`, `SUPPORT`, `ADMIN`, `SUPER_ADMIN`.
Workspace role: `OWNER`, `ADMIN`, `MANAGER`, `MEMBER`, `VIEWER`.
The schema reserves both scopes. Role enforcement for business resources is implemented in Phase 5, not implied by the existence of enum values.

## Coding standards
- TypeScript strict mode in the frontend; DTOs and service boundaries in backend.
- Keep React components feature-scoped; shared primitives belong in `components/`.
- Never put provider credentials in `VITE_*` variables or browser storage.
- Never fabricate dashboard/analytics values; compute from persisted domain records.
- Every tenant-owned database row must carry a workspace foreign key and every query must scope by the authenticated membership.
- Database changes require a committed migration.
- No placeholder buttons, fake integrations, sample production records or silent error swallowing.

## Testing requirements
- Frontend: typecheck, production build, component tests, form validation, responsive smoke tests.
- Backend: DTO validation, auth service unit tests, API integration tests against PostgreSQL, session expiry/revocation, token expiry/one-time use, TOTP/recovery code tests, rate-limit tests.
- Security: cross-user session isolation, unauthorized access, suspended user denial, email enumeration resistance, secret leakage checks, dependency audit.
- Release gate: `npm run typecheck`, `npm run build`, `npm --prefix backend run build`, `npm --prefix backend test`, Prisma migration deploy and end-to-end smoke tests all pass.

## Known deliberate boundaries after Phases 0–3
Business workspace records are still local browser preview data. The workspace/member tables are only the foundation; there are no workspace CRUD or project/task/customer/invoice APIs yet. Admin console, RBAC enforcement, production email delivery, cloud backups and production deployment are not claimed complete.

## Phase 4–7 domain modules

- `users`: authenticated profile read/update.
- `workspaces`: workspace CRUD, member listing, invitation lifecycle, role assignment and membership enforcement.
- `common/roles.ts`: canonical workspace role-to-permission matrix and optional route guard.
- `projects`: workspace-scoped project CRUD, milestone lifecycle and activity history.
- `dashboard`: read-only aggregation of workspace projects, tasks, invoices, customers and upcoming events.

Workspace-owned records carry a `workspaceId`. Services first verify that the caller is a member of that workspace and then include the same `workspaceId` in every record query/mutation. The frontend's local preview records are also keyed by both user ID and workspace ID; they remain explicitly non-cloud data until their corresponding CRUD phases are implemented.
